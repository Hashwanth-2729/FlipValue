# Valuation methodology — `comparables-v1`

Implemented in `src/flipvalue/engine.py`. The version string is returned as `method` (partner API) and
`method_version` (website) and is part of every `valuation_id`.

## Inputs

Model (exact catalogue match), storage (exact), region/currency (IN/INR or US/USD), condition grade, faults,
optional repair type, optional age. Freshness window `FLIPVALUE_FRESHNESS_DAYS` (default 180) ending today.

## Comparable selection

Observations with the **same model, storage, region and grade**, `observed_at` within the window and not in the
future. Nothing is pooled across storage sizes, regions, currencies or grades.

* Storage omitted: used only when the model has exactly one catalogued variant; otherwise `no_data_for_condition`
  ("storage_gb is required").
* Storage not catalogued for the model: `no_data_for_condition`.

## Price basis (never mixed)

Resale estimates use the first basis with ≥ 3 observations, in this order:

1. `completed_sale`
2. `listing` (asking prices; always labelled and always "limited")
3. `estimate`: FlipValue modelled estimates (see below; quality "modelled", confidence "low", always labelled)
4. `synthetic`: only when mock data is allowed (never in production)

`dealer_offer` and `trade_in` observations are summarised separately as the buyback value (see "Value types"),
never as resale. Without either, the buyback value falls back to `estimate_buyback`.

## Modelled estimates (added 2026-10-28)

Without enough sales for most phones, every catalogued model gets a labelled, modelled estimate
(`src/flipvalue/estimates.py`, regenerated by `python -m flipvalue load-estimates` and by `release` on every deploy).

* **Input:** `data/estimates/price_bands.csv` holds, per model and base storage, the launch price and approximate
  current new, refurbished and used price ranges. Twenty rows come from the owner's ranges of 2026-10-28; where those
  were inconsistent (used above refurbished, new above launch), the cap is noted in the `basis` column. Eleven rows are
  derived from the manual Cashify, Budli and Flipkart price checks using typical ratios.
* **Grade:** from the used range [L, H]: excellent H, good (L+H)/2, fair L, poor 0.75 L, faulty 0.45 L.
* **Storage:** +8% per larger catalogued variant (used and refurbished), +10% (new and MRP).
* **Buyback:** 70% of the private-sale estimate for the same grade.
* **Valuation:** the engine uses only the latest month's three points (estimate ±6%). The range is therefore a
  modelling margin, not a spread of observed prices.
* **History (trends):** one month per point since release, declining exponentially from 80% of the launch price to
  today's estimate, with a small fading wiggle. It shows the general depreciation shape, not actual past prices.
* **Store prices (comparison):** one price per store inside the range (new: Amazon, Flipkart, Croma, Reliance
  Digital, the brand's store, with MRP = launch price; refurbished: Cashify, Amazon Renewed, Budli, Controlz; used:
  OLX, Quikr, Facebook Marketplace; buyback: Cashify, Budli). Each store's position in the range is a stable hash, so
  prices don't change between page loads. They have no links, never age out, never create alerts and never enter
  observed price history.
* **Labelling:** the API returns `basis: "estimate"`, `quality: "modelled"`, a warning, and `source.estimated` on
  offers. The website shows an "Estimate" badge, a site banner and a result notice. Real observations always win
  when there are enough of them. `refurbished_retail` and `customer_quote` observations are stored with provenance but not used in
this version; refurbished retail values come from marketplace offers.

## Statistics

* `value` = median.
* n ≥ 10: `low`/`high` = 10th/90th percentile (inclusive linear interpolation, Python `statistics.quantiles`).
* 3 ≤ n < 10: `low`/`high` = minimum/maximum.
* n < 3: no estimate (`no_data_for_condition` on the partner API; an "unavailable" result on the website).
* Money rounded half-up to 2 decimals. `low ≤ value ≤ high` always holds.

## Quality

* `evidence_backed`: completed sales (or synthetic, for development parity), n ≥ 10, newest ≤ 90 days old.
* `limited`: anything else that still produced an estimate.

The website never labels synthetic estimates as evidence: it shows "Mock data · not evidence". These are evidence
descriptions, not statistical confidence; no accuracy has been measured (no real data exists to measure it).

Partner `status` is `partial` when any returned estimate is `limited`, or `after_repair` was requested but unavailable.

## Condition and faults

The grade carries condition. Faults do **not** adjust prices — there is no evidence for fault-specific discounts —
and a warning says so. On the website the questionnaire maps to a grade by the contract definitions
(`condition.py`): any reported functional problem → `faulty`; otherwise the worse of screen and body.

## Age

Not used. Recent comparables of the same model already reflect that model's age; per-device age has no evidence
behind an adjustment. A warning is added when `age_months` is sent.

## After repair

Target grade: `faulty` → `good`; any other grade unchanged (a repair restores function, not cosmetics). Estimated
from comparables in the target grade, same rules. Assumes the repair is done well; excludes repair cost.

## Reproducibility

`valuation_id = "val_" + sha256(method version, canonical request, sorted observation ids used)[:24]`. Every
observation keeps source, ingestion job, external reference, observation and collection timestamps, so any
estimate can be recomputed from the database.

`data_timestamp` (partner) = newest observation date used, as midnight UTC.

## Value types (`/api/v1/valuations` and the website's "Other kinds of value")

Implemented in `services.py` on top of the engine. Each type has its own evidence; they are never averaged.

| Type | Evidence | Unavailable when |
|---|---|---|
| `private_sale` | Engine estimate above (completed sales, else asking prices) | < 3 comparables |
| `buyback` | First basis with ≥ 3 observations of `dealer_offer`, then `trade_in`, same model/storage/region/grade | No such observations. Today they can only come from manual records (no buyback provider allows automated access) |
| `refurbished_retail` | Median (min–max range) of current `exact`/`strong` refurbished offers of the exact variant, in stock or unknown stock | No current offer. It is a refurbisher's asking price, not what a seller receives |
| `original_retail` | Median of retailer-supplied MRP on current new offers of the exact variant | No MRP supplied. No launch prices without a source |
| `after_repair` | Engine estimate in the post-repair grade | < 3 comparables in that grade |

`repair.value_uplift = after_repair.value − private_sale.value`, only when both exist. It is an observed price
difference between grades for this model, not a universal percentage, and excludes the repair cost. When either side
lacks evidence, the uplift is `null` with an explanation.

### Confidence classes

| Class | Rule |
|---|---|
| `high` | Evidence-backed: ≥ 10 completed sales, newest ≤ 90 days |
| `medium` | 3–9 completed sales, or ≥ 10 observations of a non-listing basis; offers: ≥ 5 current offers |
| `low` | Asking prices, 3–9 non-sale observations, 1–4 offers, or any synthetic/fixture data |
| `insufficient` | No estimate |

These describe the amount and kind of evidence. **No predictive accuracy has been measured**: there is no labelled
real dataset to evaluate against, so no model was trained and none is claimed. Next step once real completed sales
exist: back-test medians against later sales (median absolute percentage error per model and grade) and only then
consider a statistical model, compared against this transparent baseline.

Every v1 valuation also returns `assumptions`, `limitations`, `missing_data` and `how_to_improve`.
